# Meal Planner — Backend

FastAPI + PostgreSQL + MinIO backend for a recipe app, fully containerized.
Built as a Docker/Kubernetes learning project — this is the v1 backend (recipe
CRUD + image upload + JWT auth). A React Native iOS frontend and Kubernetes
migration come next.

## Stack

- **API:** Python / FastAPI
- **Database:** PostgreSQL (via SQLAlchemy + Alembic migrations)
- **Object storage:** MinIO (S3-compatible, for recipe images)
- **Auth:** email/password with JWT

## Data model

- `User` — id, email, password_hash
- `Recipe` — title, description, prep/cook time, servings, image_url, is_public
- `Ingredient` — global catalog (e.g. "garlic"), reused across recipes
- `RecipeIngredient` — join table: quantity (numeric, optional) + unit (free text, e.g. "pinch", "cups") + notes
- `RecipeStep` — ordered instructions per recipe
- `Tag` / `RecipeTag` — many-to-many tagging (e.g. "vegetarian", "quick")

## Running it

1. **Copy the env file and fill in real secrets:**
   ```bash
   cp .env.example .env
   ```
   At minimum, change `JWT_SECRET_KEY` to a long random string before you
   ever deploy this anywhere beyond your own machine.

2. **Start everything:**
   ```bash
   docker compose up --build
   ```
   This starts the API (port 8000), Postgres (port 5432), and MinIO
   (port 9000 for the S3 API, 9001 for its web console).

3. **Run the database migration** (first time only, in a separate terminal):
   ```bash
   docker compose exec api alembic upgrade head
   ```

4. **Check it's alive:**
   ```bash
   curl http://localhost:8000/health
   ```

5. **Interactive API docs** (auto-generated by FastAPI):
   Open `http://localhost:8000/docs` in a browser — you can register, log in,
   and test every endpoint from there without writing any client code.

### Optional: pgAdmin

A pgAdmin container is included but doesn't start by default. To bring it up:
```bash
docker compose --profile tools up
```
Then visit `http://localhost:5050` (login: `admin@example.com` / `admin`,
as set in docker-compose.yml — change these before using this anywhere
shared).

## API overview

```
POST   /auth/register
POST   /auth/login          → returns JWT (use as "Bearer <token>")

GET    /recipes             → list current user's recipes
POST   /recipes             → create recipe (with nested ingredients/steps/tags)
GET    /recipes/{id}
PUT    /recipes/{id}
DELETE /recipes/{id}

POST   /recipes/{id}/image  → multipart upload, stores to MinIO

GET    /tags
```

All `/recipes` and `/tags` endpoints require `Authorization: Bearer <token>`
except where noted.

## Making schema changes

This project uses Alembic for migrations — don't hand-edit the database.
After changing anything in `app/models.py`:

```bash
docker compose exec api alembic revision --autogenerate -m "describe your change"
docker compose exec api alembic upgrade head
```

Always read the generated migration file before applying it — autogenerate
is a good first draft, not a guarantee.

## Notes on decisions made here

- **Ingredient quantities are structured-but-flexible**: `quantity` is a
  nullable float, `unit` is free text. So "2 cups flour" and "salt, a pinch"
  both work naturally, at the cost of not being able to do perfect
  unit-aware math later (e.g. auto-generated grocery lists). That tradeoff
  was intentional for v1.
- **Auth is plain JWT**, not OAuth/Sign in with Apple — kept simple so the
  focus stays on the Docker/Kubernetes side of this project rather than
  iOS-specific auth flows.
- **Passwords are hashed with `bcrypt` directly** (not `passlib`), since
  `passlib` is unmaintained and breaks with recent `bcrypt` releases.
- **Image URLs are presigned MinIO URLs** (7-day expiry). Fine for a
  personal project; in a real production setup you'd put a reverse proxy
  or CDN in front of the bucket instead of relying on presigned links.
